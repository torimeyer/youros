The Problem

AI agents are ungoverned

👤

No standard agent identity

There's no standard way to prove an agent is who it says it is, who authorized it, or what it's allowed to do.

⚙

Governance requires a lot of infrastructure

Identity provisioning, permission models, scope management, admin controls. Real engineering work for every agent you ship.

🔄

No coordination

Nothing stops two engineers from assigning agents to the same problem. No shared task queue, no "already in progress" signal.

💰

Agents waste tokens

Without compression and coordination, agents use far more tokens than they need to get the job done. That's a direct cost problem at scale.

The Solution

ostk is the kernel for AI agents

A kernel is the core of an operating system. It's the permanent layer underneath everything else that controls who can do what, prevents things from colliding, and keeps a record of everything that happens.

Right now, AI agents run without a kernel. Nothing controls their access, nothing prevents conflicts, nothing logs what they did. ostk is that missing layer. It gives agents identity, permissions, coordination, and audit trails that satisfy compliance requirements out of the box.

Language

How ostk names things

ostk uses a consistent metaphor. Once you know five words, you know the whole system.

Term What it means
Needle A task. Something that needs to get done. Has a priority, an owner, and a status.
Hay A raw idea. Unstructured thinking that hasn't become a task yet. You capture it now, organize it later.
Tack ostk's shorthand language. Short commands that compress intent into a few words instead of long instructions.
Pin A permission ruleset. Defines exactly what an agent can read, write, and run. Denied by default.
Bail A signed, portable package. Everything needed to set up ostk in a new project, verified and tamper-proof.

"Find the needle in the haystack." Tasks are needles. Raw ideas are hay. ostk helps you find and organize the work.

In Practice

What happens when an agent runs through ostk

1

Engineer gives an agent a task

"Fix the login bug in the auth service." The engineer's identity is recorded in the HUMANFILE with their trust tier. ostk spawns the agent with a model, a budget cap, and a permission set (pin) that controls what the agent can access.

2

ostk queues the task

The agent claims the task from the queue using `needle pull`. This gives each agent the next available task, reducing duplicate work. The spawn event is logged to the audit trail.

3

The agent works within its permissions

Each agent has a ruleset that lists exactly which folders and files it can access. If it tries to touch anything outside that list, it's blocked. If two agents edit the same file, ostk automatically combines both changes without losing either one.

4

Agent finishes, ostk closes the loop

Task marked complete in the audit trail. Session shutdown is logged. The full history of task lifecycle events (created, assigned, completed) is available for review or export.

Design Constraints

Five laws of agent coordination

These are not guidelines. They are load-bearing constraints. If a feature violates a law, the feature is wrong.

1

Invisible write path

Agents edit files normally. The OS intercepts, coordinates, and audits underneath. No new API. No SDK. No coordination protocol.

2

Agents are ephemeral

Agents crash. They hit context limits. They get killed. State lives in the filesystem, not the agent. A new one picks up where the last stopped.

3

Filesystem is the bus

No message buses. No pub/sub. No RPC. Agents coordinate by reading and writing files. Every coordination artifact is inspectable.

4

Optimistic concurrency

No locks. Agents write freely and concurrently. When two agents edit the same file, the kernel resolves the conflict. Resolution, not prevention.

5

Invisible infrastructure

If you have to think about the OS, the OS failed. One command to install. One to init. One to boot. After that, it disappears.

Built-in Observability

Every agent action is observable

  • Structured event log that records when tasks are created, assigned, and completed, when agents are spawned, and when sessions end.
  • Agent spawn tracking records which model was used, what budget was set, and when it started.
  • Budget caps set at spawn time so agents can't run up unlimited costs.
  • Live agent status via `kernel ps` shows what's running right now.
  • Dead agent cleanup via `kernel reap` removes agents that stopped responding.
  • Real-time TUI via `ostk tui` shows agents executing, files resolving, and permissions gating in real time.

Governance & Security

Enterprise-grade agent governance

🔒

Verified identity

Every user has a HUMANFILE with their identity and trust tier. Governance documents are GPG-signed. No personal data is collected. Identity is about accountability, not surveillance.

🛡

Locked-down permissions

Pins define what each agent can read, write, and execute. When set, everything not explicitly allowed is blocked. An agent working on one project can't touch another.

📜

Compliance-ready audit trail

Task and agent lifecycle events are logged automatically with timestamps. The log is append-only and exportable. Built to meet requirements like the EU AI Act's mandate for automatic, tamper-resistant AI system logs.

🛠

Three-tier conflict resolution

When agents make conflicting edits: (1) non-overlapping changes merge silently, (2) overlapping changes get a suggested merge, (3) true conflicts flag for retry. No lost work.

Guardrails

Dangerous commands get caught

When an agent tries to run a destructive operation, the kernel pauses it and gives the operator 60 seconds to approve or cancel.

Category Caught commands
Infrastructure terraform destroy, pulumi destroy
Database DROP TABLE, TRUNCATE
Filesystem rm -rf, find -delete
Containers kubectl delete namespace
Cloud aws s3 rm --recursive
Git git push --force origin main

Three Modes

confirm

Queue the command, notify the operator, execute after 60s if no response. Default.

deny

Block entirely. The agent cannot run destructive commands.

allow

Pass through. Not recommended for production.

The question is never "can we trust this agent with production?" It's "what controls exist around destructive actions?"

Under The Hood

How ostk reduces token usage

1

Output compression

A three-layer pipeline strips visual noise, collapses repeated output (like 200 "Compiling..." lines into one summary), and preserves only the signal (errors, warnings, results).

2

Skip what hasn't changed

If an agent already read a file and it hasn't changed, the kernel says "you already have this" instead of sending the full content again. No wasted tokens on redundant reads.

3

Intent compression

The tack language compresses commands from ~200 tokens of natural language down to ~10 tokens of shorthand. The kernel resolves intent, not instructions.

The agent doesn't know this is happening. It reads, writes, and runs commands normally. The kernel compresses everything invisibly underneath.

Concrete Example

An MCP server, without API keys

Today's approach

  • User provides their personal API key to the MCP server
  • The server calls APIs as that user
  • No separate identity for the integration itself
  • Admins have limited control over what the integration can do
  • Repeat for every partner integration

With ostk bails

  • Vendor creates an Agentfile defining the MCP server (tools, limits)
  • Permissions set via pins (what it can read, write, execute, and what's denied)
  • API credentials stored in vault, referenced by HUMANFILE, never exposed
  • Everything GPG-signed into a bail. Customers verify offline.
  • No personal API key needed. One signed package is the identity, the permissions, and the governance.

Every partner agent, every integration, every MCP server becomes a signed, verifiable, auditable package. Ship once, verify anywhere, no infrastructure needed.
